# Data Model: Phase I - Console Todo Application

**Feature**: Phase I Console Todo Application
**Date**: 2026-01-02
**Source**: [spec.md](./spec.md) | [plan.md](./plan.md)

## Overview

Phase I uses in-memory storage with Python's built-in data structures. The data model is intentionally simple to avoid over-engineering while meeting all functional requirements. No database schema or ORM is required - all data lives in memory for the duration of the application session.

## Entities

### Task

**Purpose**: Represents a single todo item with title, description, and completion status.

**Fields**:

| Field Name | Type | Required | Constraints | Default | Description |
|-----------|------|----------|-------------|---------|-------------|
| `id` | `int` | Yes | Positive integer, unique, auto-generated | N/A (generated) | Unique identifier for the task, assigned sequentially starting from 1 |
| `title` | `str` | Yes | 1-500 characters, non-empty, no leading/trailing whitespace | N/A | Brief description of what needs to be done |
| `description` | `str` | No | 0-2000 characters, can be empty | `""` (empty string) | Optional detailed information about the task |
| `status` | `TaskStatus` | Yes | Must be `INCOMPLETE` or `COMPLETE` enum value | `TaskStatus.INCOMPLETE` | Indicates whether the task has been completed |

**Validation Rules**:
1. **Title Validation**:
   - MUST NOT be empty string after stripping whitespace
   - MUST be at least 1 character long
   - Maximum 500 characters
   - If exceeds 500 characters, truncate with "..." indicator (per spec edge cases)

2. **Description Validation**:
   - CAN be empty string (optional field)
   - Maximum 2000 characters
   - If exceeds 2000 characters, truncate with "..." indicator (per spec edge cases)

3. **ID Validation**:
   - Auto-generated by TaskService, starts at 1
   - Increments sequentially for each new task
   - Never reused after task deletion (sequential counter continues)
   - Immutable once assigned (cannot change task ID)

4. **Status Validation**:
   - MUST be one of: `TaskStatus.INCOMPLETE` or `TaskStatus.COMPLETE`
   - Enum enforcement prevents invalid status values
   - Default to `INCOMPLETE` when task is created

**Python Implementation**:
```python
from dataclasses import dataclass
from enum import Enum

class TaskStatus(Enum):
    """Task completion status"""
    INCOMPLETE = "Incomplete"
    COMPLETE = "Complete"

@dataclass
class Task:
    """Represents a single todo task"""
    id: int
    title: str
    description: str
    status: TaskStatus
```

### TaskStatus Enum

**Purpose**: Type-safe representation of task completion states.

**Values**:
- `INCOMPLETE`: Task has not been completed (default state)
- `COMPLETE`: Task has been completed

**Rationale**: Enum prevents invalid status values and provides clear, type-safe state management. Only two states required for Phase I per specification.

## Storage Strategy

### In-Memory Storage

**Data Structure**: Python dictionary (`dict[int, Task]`)

**Key**: Task ID (integer)
**Value**: Task object (dataclass instance)

**Example**:
```python
{
    1: Task(id=1, title="Buy groceries", description="Milk, eggs, bread", status=TaskStatus.INCOMPLETE),
    2: Task(id=2, title="Finish report", description="Q4 financial report", status=TaskStatus.COMPLETE),
    3: Task(id=3, title="Call dentist", description="", status=TaskStatus.INCOMPLETE)
}
```

**Storage Characteristics**:
- **Lifecycle**: Exists only during application runtime (no persistence)
- **Capacity**: Up to 1000 tasks per session (per spec assumptions)
- **Performance**: O(1) average case for lookup, insert, update, delete by ID
- **Thread Safety**: Not required (single-user, synchronous operations per Phase I constraints)

### ID Generation Strategy

**Approach**: Simple sequential counter

**Implementation**:
```python
class TaskService:
    def __init__(self):
        self._tasks: dict[int, Task] = {}
        self._next_id: int = 1

    def add_task(self, title: str, description: str) -> Task:
        task_id = self._next_id
        self._next_id += 1
        task = Task(id=task_id, title=title, description=description, status=TaskStatus.INCOMPLETE)
        self._tasks[task_id] = task
        return task
```

**Characteristics**:
- Starts at 1 (user-friendly, matches common numbering conventions)
- Increments by 1 for each new task
- Never reused (even after task deletion, counter continues)
- Simple and predictable (user can easily remember IDs)

**Rationale**: Sequential IDs are simpler than UUIDs for single-user, non-distributed systems. Users can easily reference tasks by small integer IDs (1, 2, 3...) rather than long UUID strings.

## State Transitions

### Task Status Lifecycle

```
                    ┌──────────────┐
                    │              │
         ┌─────────►│  INCOMPLETE  │◄─────────┐
         │          │   (default)  │          │
         │          │              │          │
         │          └──────────────┘          │
         │                  │                 │
         │                  │ Mark Complete   │
         │                  │                 │
         │                  ▼                 │
         │          ┌──────────────┐          │
         │          │              │          │
         │          │   COMPLETE   │          │
         │          │              │          │
         │          └──────────────┘          │
         │                  │                 │
         │                  │                 │
         │                  └─────────────────┘
         │                  Mark Incomplete
         │
         └──────────────────────────────────────
                     (Delete task removes from storage)
```

**Valid Transitions**:
1. **Task Creation**: → `INCOMPLETE` (default state)
2. **Mark Complete**: `INCOMPLETE` → `COMPLETE`
3. **Mark Incomplete**: `COMPLETE` → `INCOMPLETE`
4. **Task Deletion**: Any state → Removed from storage

**Toggle Logic**:
```python
def toggle_status(self, task_id: int) -> Task:
    task = self.get_task_by_id(task_id)  # raises TaskNotFoundError if not found
    if task.status == TaskStatus.INCOMPLETE:
        task.status = TaskStatus.COMPLETE
    else:
        task.status = TaskStatus.INCOMPLETE
    return task
```

## Data Validation

### Input Validation Layers

**Layer 1: CLI Presentation Layer**
- Validates input format (integer IDs, non-empty strings)
- Checks length constraints (title ≤500, description ≤2000)
- Provides immediate user feedback for format errors

**Layer 2: Service Business Logic Layer**
- Validates business rules (task exists, title not empty after strip)
- Enforces data integrity (no duplicate IDs, status must be enum value)
- Raises typed exceptions for validation failures

### Validation Examples

**Valid Inputs**:
```python
# Valid task creation
add_task(title="Buy groceries", description="Milk, eggs, bread")  # ✓
add_task(title="Call dentist", description="")  # ✓ Empty description allowed
add_task(title="A", description="")  # ✓ Single-char title allowed

# Valid updates
update_task(task_id=1, title="Buy groceries and snacks", description=None)  # ✓
update_task(task_id=1, title=None, description="Update description only")  # ✓
```

**Invalid Inputs**:
```python
# Invalid task creation
add_task(title="", description="Test")  # ✗ Empty title → InvalidInputError
add_task(title="   ", description="Test")  # ✗ Whitespace-only title → InvalidInputError
add_task(title="A" * 501, description="")  # ✗ Title too long → Truncated with "..."

# Invalid operations
get_task_by_id(task_id=999)  # ✗ Task doesn't exist → TaskNotFoundError
update_task(task_id=1, title="", description=None)  # ✗ Empty title → InvalidInputError
```

## Performance Characteristics

### Time Complexity

| Operation | Complexity | Rationale |
|-----------|-----------|-----------|
| Add Task | O(1) | Dictionary insert by key |
| Get Task by ID | O(1) | Dictionary lookup by key |
| Get All Tasks | O(n) | Iterate all dictionary values (n = number of tasks) |
| Update Task | O(1) | Dictionary lookup + in-place update |
| Delete Task | O(1) | Dictionary deletion by key |
| Toggle Status | O(1) | Dictionary lookup + enum value change |

### Space Complexity

| Component | Space | Notes |
|-----------|-------|-------|
| Task Object | ~266 bytes | id (8B) + title (~50B avg) + description (~200B avg) + status (8B) |
| Dictionary Storage | O(n) | n = number of tasks, ~340KB for 1000 tasks |
| ID Counter | O(1) | Single integer (8 bytes) |
| **Total** | **~340 KB** | For 1000 tasks (max capacity per spec) |

**Performance Validation**:
- ✅ Meets <500ms p95 latency requirement (actual: <10ms for O(1) operations)
- ✅ Meets 1000 task capacity requirement (well within memory constraints)
- ✅ Meets <15s add task requirement (actual: <1ms)
- ✅ Meets <3s view list requirement (actual: <100ms for 1000 tasks)

## Constraints & Assumptions

### Phase I Constraints

**Storage Constraints**:
- In-memory only (no file persistence, no database)
- Data lost when application exits (expected behavior per spec)
- Single user (no concurrent access, no locking required)
- Maximum 1000 tasks per session (reasonable limit for in-memory console app)

**Data Constraints**:
- Sequential integer IDs only (no UUIDs, no custom ID schemes)
- Two status values only (INCOMPLETE, COMPLETE - no additional states)
- No relationships between tasks (no subtasks, no task dependencies)
- No metadata (no creation timestamps, no modification timestamps, no user attribution)

### Assumptions

**Data Assumptions**:
- Users will remember task IDs from viewing the list (IDs displayed in View Tasks)
- Average title length: 50 characters
- Average description length: 200 characters
- Typical session: <100 tasks created

**Technical Assumptions**:
- Python 3.11+ guarantees dict ordering (insertion order preserved)
- Python dict is efficient for up to 10,000+ items (1000 task limit is safe)
- No need for data migration or versioning in Phase I

## Future Evolution (Phase II+)

**Not Implemented in Phase I** - Planning considerations only:

**Phase II Migration Path**:
1. **Storage**: In-memory dict → SQLModel ORM with Neon DB (PostgreSQL)
2. **IDs**: Sequential int → UUID for distributed systems
3. **Metadata**: Add created_at, updated_at timestamps
4. **User Attribution**: Add user_id foreign key for multi-user support
5. **Relationships**: Add task categories, tags, priorities

**Migration Strategy** (Phase II):
- Extract storage interface for dependency injection
- Implement database-backed storage implementing same interface
- Keep in-memory implementation for testing
- Zero changes required to business logic layer (service layer)

**Note**: These are planning considerations for future phases. Phase I implements only the minimal data model described above per constitutional phase governance requirements.
